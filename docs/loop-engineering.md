# Loop Engineering · Ordine 项目的持续优化方法论

> 2026-06-13 沉淀。本文档把 N11–N20 十几轮协作中**真正起作用的工作方式**提炼成一套可复用的循环，作为本项目后续所有迭代的元规则（meta-rule）。它与 `CLAUDE.md` 的施工纪律互补：CLAUDE.md 规定"一期工程怎么做"，本文档规定"每一轮怎么转起来、靠什么收敛"。

## 一、自指的发现

N20 让 Agent 用 `loopEnabled` operation 实现"生成 → 自我批判 → 改进直到 PASS"的验证环。回头看，**我们的协作过程与它同构**：

```
用户给目标/反馈  →  证据级审查  →  施工计划入库  →  逐任务实现+commit  →  真机验证(PASS/FAIL)
       ↑                                                                              │
       └──────────────────── 失败或新发现 → 进入下一轮（带反馈重做）───────────────────┘
```

N20 那个 operation 的 `loopConditionPrompt` 写的是"输出 PASS；只要还存在任何一处可改进的问题，输出 FAIL 并列出具体问题，下一轮带反馈重做"——这正是用户每次发"还有什么要修的 / 继续下一期 / 三张截图反馈"时在做的事。**Loop Engineering 就是把这个隐式循环显式化、并守住它的收敛条件。**

## 二、循环的五个相位

| 相位 | 做什么 | 收敛信号 | 反模式（必须避免） |
|---|---|---|---|
| **Input** | 接住目标或反馈，不急着写码 | 目标可被拆成可验收的子项 | 把模糊目标直接当任务做 |
| **Audit** | 证据级现状审查（`文件:行号`） | 改什么有代码证据，不是"大概在某处" | 凭印象动手 |
| **Plan** | 施工计划入手册，一任务=一 commit 量 | 每任务四要素齐（改动/做法/验收/i18n） | 边想边改，无计划 |
| **Build** | 逐任务实现，每任务单独 commit | tsc + i18n 检查全绿 | 一个大 commit 混多件事 |
| **Verify** | **真机**走通主路径（真模型，非单测绿） | PASS：真机复现达标；FAIL：记入下一轮 | 单测绿就收工 |

## 三、五条铁律（每条都救过场）

### 1. 证据级审查先行——它比写码更值钱
- **N14-03**：真机发现提案反复校验失败。审查追到 `PROPOSE_SYSTEM_PROMPT` 从未文档化各 nodeType 的必填字段——模型只能瞎猜，凡带输入节点的提案必挂。补全字段说明，第三轮一次过。**这个根因不审查永远找不到。**
- **N20-00**：compound 节点 schema 看起来完整（verify/council/delegation 三型），差点去"实现 compound 提案"。审查追到引擎层 `Pipeline.ts:452 // compound — passthrough for now`——空壳。**改用真实可执行的 operation loop，避免了让 Agent 画出引擎会跳过的结构。**

### 2. "不伪造"是不可逾越的红线（CLAUDE.md / 手册警告 4）
展示的必须等于真实发生的。这条贯穿每一期：
- N12 ContextStrip 假透明（展示 8 项、实发 2 项）→ 改单一事实源
- N14 reversing 假 done 动画 → 改真实阶段事件
- N18 不放假开关（routine 通知无触发源、Limits 无成本统计 → 干脆不放）
- N20 不放开空壳 compound
- **判据**：如果界面上有一个东西，运行时却没有对应行为，它就是 bug，不是 feature。

### 3. 真机验证是循环的唯一收敛条件
单测绿 ≠ 完成。真机才是 `loopConditionPrompt`：
- **N19-02**：清除历史按钮单测、tsc 全过，真机才发现它被 ProjectSection"未选项目"早返回遮挡（且 hooks 写在早返回后违反规则）。拆独立组件才修好。
- **N18/G3 全程**：用 Chrome 自动化 + JS 原生事件真点，多次抓到纯单测发现不了的渲染/数据/交互缺陷。

### 4. 误报也要诚实标注、撤销并复证
- G3-02（Jobs 行点击"死"）、G3-04（Usage 筛选"假"）真机复查后判定为**误报**（前者是浏览器缩放+翻译插件干扰自动化坐标，后者是 0-token run 的数据巧合），在清单里显式撤销。**诚实的"这其实没坏"和诚实的"这坏了"同等重要。**

### 5. 遗留显式记录，绝不静默跳过
每期末把没做完的写进手册遗留清单（带原因和方向）：compound 引擎三型、N15-02 流式、跨会话记忆、vite SSR 热重载崩溃。**下一轮可以直接接续，不丢上下文。**

## 四、协作层面的两个加速器

- **手册是唯一事实源**：`docs/ordine-agent-bar重构手册v3.md` 记录每期计划+执行+commit+遗留，任何一轮都能从它恢复全貌。验收记录沉淀在 `pr-assets/`。
- **并行不踩脚**：与 claude code 的 format/quality 批次并行时，提交一律按文件精确 `add`，先核验对方改动安全再收编（如 `54b2918b`），不 rebase 打乱提交。

## 五、用本方法论看"下一步该做什么"

按"价值 × 是否阻断收敛"排序的候选池（持续更新）：

1. **N20-03 收尾（轻、闭环价值高）**：真模型 Run 一条带 loop 的流水线，核验 trace 有 `[Loop] Iteration k/N` 与条件 PASS/FAIL——这是 N20"不伪造"的最后一块铁证，逻辑现成（`OperationNode.ts:227`）。
2. **工程效率（中、已反复阻断）**：vite 对 packages/services 的 SSR 热重载崩溃已累计 4–5 次，每次改服务端都要手动重启——根治它能让后续每一轮 Verify 相位更顺。
3. **跨会话记忆（大、点亮 Strip memory 项）**：N12 决策 5 的遗留，做完后 ContextStrip 的 memory 项才能名正言顺点亮。
4. **compound 引擎三型执行（远期大工程）**：verify/council/delegation 各需一套子图执行协议，体量等同一个 N 期。
5. **质量门收口（每期遗留）**：宿主机集中跑 `bun run format` + `bun run quality`，把沙盒跑不了的 vitest/oxlint 补齐。

**推荐**：先做 1（闭环 N20）+ 2（根治热重载），它们让循环本身转得更稳；再按用户优先级在 3/4 里选一个大方向。
