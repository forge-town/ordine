# Ordinctor 代码治理审查与改动计划

> 2026-06-12 · 基线 commit：`refactor/canvas-v2` @ N11 系列 · 审查范围：`apps/app`、`apps/server`、`packages/*` 活跃源码（46.5k 行，不含 archived/测试/stories）
> 方法：全量结构扫描（行数分布、依赖方向、模式抽样）+ 既有规范（CodeGuidelines / 施工手册 §三铁律）逐条对照。每条发现给出证据位置；改动计划按"速赢 → 结构 → 长期"三期编排，颗粒度对齐施工手册（一任务一 commit、可独立验收）。

---

## 一、总体结论

仓库的**分层骨架是健康的**：`schemas → db-schema → models → services → 路由 → UI` 单向依赖成立（schemas 零业务 import，实测干净）；neverthrow 纪律执行得非常好（全仓业务代码仅 2 处 try-catch，均在边界工具包）；新增代码（Canvas V2 / Jobs 控制台 / AgentBar）普遍带测试与 i18n。

主要债务集中在三类：**①"注册表式"代码长成了巨石**（dataProvider 876 行 80 个 case、pipelinesService 762 行五种职责）；**②同一问题的多种写法并存**（三种 store 形态、两套 i18n 标准、六处重复 formatter）；**③重构遗留未清算**（444 个 archived 文件留在 src、knip/死键未跑、一处 feature 间反向依赖）。这些都不是结构性腐坏，而是高速施工期的正常沉积，现在清算成本最低。

## 二、架构层发现（A 系列）

### A1 · 数据访问"三轨制"：一个资源要在三处登记

- 证据：`apps/app/src/integrations/refine/dataProvider.ts` **876 行、80 个 `case ResourceName.*`** 的手写 switch；同一资源同时存在 Hono 路由（`apps/server/src/routes/*.ts`）与 tRPC router（`apps/app/src/integrations/trpc/routers/*.ts`）。
- 后果：新增一个实体要改 dataProvider 的 getList/getOne/create/update/deleteOne 五个 switch 分支 + tRPC router + Hono 路由 + ResourceName 枚举，遗漏任何一处都是运行时才暴露的 `unknown resource` 异常（字符串路由 `"jobs/pause"` 这类 custom url 更是纯约定，无类型保护）。
- 定性：**最高优先级的结构债**。它是每个后续功能的"过路费"。

### A2 · 包边界命名噪声

- 证据：`packages/` 下同时存在 `agent` 与 `agent-engine`、`plugin` 与 `plugins`、`shared` 与 `utils`、以及注释为"desktop 专用暂不动"的 `views`。
- 后果：新人（含 coding agent）无法从名字推断职责归属，跨包搬代码时容易放错层。
- 定性：低频痛但长期累积认知税。

### A3 · 服务层巨石

- 证据：`packages/services/src/pipelinesService/createPipelinesService.ts` **762 行**，同一工厂内并存五种职责：CRUD 透传（:275-297）、`proposeActions`（:298）、`optimizeFromDistillation`（:304-）、`analyzeIntent`（:473-）、`generateStructure`（:564-）。`createPipelineRunnerService` 同样在工厂内自装配 12 个 DAO。
- 后果：LLM 提示词工程（propose/intent/structure 都是大段 prompt 组装）与数据 CRUD 同文件演化，AgentBar 那条线的每次 prompt 迭代都在 762 行文件里做 surgical edit，冲突高发区（本周双窗口并行已验证了这一点）。

### A4 · 前端 feature 间出现一处反向依赖

- 证据：`pages/WorkspacePage/canvas/nodes/GNodeShell.tsx:18` `import { countUnresolvedAnchors, useAgentBarStore } from "../../AgentBar/_store"` —— canvas 域直接读 AgentBar 域内部 store（节点徽标计数）。
- 后果：canvas 不再可独立测试/复用；AgentBar store 重构（你正在做）会波及 canvas。这是 N5-07 落地时的捷径，应当上提到共享层（workspaceStore 已是两者的合法交汇点）。

### A5 · 状态管理三种形态并存，且单例存在跨 pipeline 泄漏面

- 证据：①Provider 工厂模式：`canvasStore`、`workspaceStore`、各页面 `_store`（约 14 个）；②模块级单例 `create()`：`agentBarStore`、`notificationStore`；③Context+createStore 混合：`toastStore`。
- 风险点：`agentBarStore` 是全局单例但承载**按 pipeline 隔离**的对话消息——靠 persistence 的 `setMessages` 覆盖来"伪隔离"，切换 pipeline 的瞬间会闪现上一条 pipeline 的消息，徽标计数同理（GNodeShell 正在读它，与 A4 叠加）。
- notificationStore/toastStore 是真全局语义，单例合理；需要的是**写下判据**而不是统一成一种。

### A6 · archived 留在 `src/` 内

- 证据：`apps/app/src/archived/` **444 个 ts/tsx 文件**。tsc 已 exclude，但 vitest 仍会跑其中的 `.unit.test`、全文搜索/IDE 索引/knip 都被它污染，且 `FolderBrowserDialog.stories` 等活跃文件仍 import 归档内模块（storybookData）。
- 定性：归档的目的已达成（git 历史保真），物理位置错了。

### A7 · 质量门资产断层

- 证据：`bun run knip` 自重构以来未清零（手册 N9-02 标记遗留）；locales **1109 个键**无死键校验；Cowork 沙盒无法跑 oxlint/oxfmt/vitest（darwin 二进制），形成"沙盒 tsc 绿 ≠ 宿主机 quality 绿"的两级现实。
- 后果：死代码与死键只增不减；双环境差异靠人记忆。

## 三、模块写法层发现（B 系列）

### B1 · 单文件行数红线（~200 行）超标清单

| 文件 | 行数 | 性质 |
|---|---|---|
| `OperationEditPage/.../OperationEditForm.tsx` | **1014** | 旧代未拆的表单巨石 |
| `integrations/refine/dataProvider.ts` | 876 | 见 A1 |
| `services/.../createPipelinesService.ts` | 762 | 见 A3 |
| `pipeline-engine/src/pipeline/Pipeline.ts` | 603 | 引擎核心，且场景测试薄 |
| `OperationCreatePageContent.tsx` | 557 | 同 B1 首条 |
| `PipelineDetailPageContent.tsx` | 524 | 旧代页面 |
| `SkillToOperationDialog.tsx` | 504 | 对话框揉了扫描+映射+提交 |
| `canvas/_store/graphSlice.ts` | 406 | compose/ungroup 几何逻辑可下沉纯函数 |
| `JobsCalendar.tsx` / `SearchPipelineDialog.tsx` / `TopPill.tsx` | 370/360/355 | 新代，数据推导与渲染未分离 |

（`sidebar.tsx`/`routeTree.gen.ts` 为 vendored/生成物，豁免。）

### B2 · i18n 双标

- 新组件（canvas chrome、Jobs 控制台、Settings 新 section）全量走 `useTranslation`；但存量页面硬编码英文仍在：`SearchPipelineDialog.tsx`（"Pipeline workspace"、"No results"…）、`ComponentsPageContent`、`SkillsPageContent`、`AppSidebar/Sidebar.tsx`、`ComponentEditor`（"Component Editor"、banner 整段）。
- 后果：zh 环境下界面中英混排，且"新组件必须 i18n"的硬规对存量无追溯，标准被稀释。

### B3 · 工具函数复制粘贴

- `formatDuration`/`formatCost`/`timeAgo`/`formatRelativeTime` 至少 **6 处独立实现**：NotificationCenter、agentRunsHelpers、PipelineCard、runSummary、JobsTable、UsagePageContent——格式不一致（"41.3s" vs "41s" vs "1m02s"）已经是可见 bug 面。

### B4 · Job 控制调用散落三处

- `JobsTable.tsx`（`jobs/${action}` 模板串）、`JobDetailDrawer.tsx`、`TopPill/CheckpointDialog`（N11-stop 后）各自手写 `dataProvider.custom + ResultAsync + toast` 三件套。语义（乐观更新、错误文案、refetch 策略）已开始漂移。

### B5 · zustand slice 类型噪声

- `as unknown as Partial<T>` 全仓 **145 处**，集中在 slice 工厂（runSlice/graphSlice/proposalSlice…）。这是 slice 泛型组合模式的已知痛点，但当前写法让每个 set 调用都带一次裸强转，类型安全形同虚设。

### B6 · dirty/相等判定靠 `JSON.stringify`

- `TopPill.tsx`（图 dirty）、`NodeConfig.tsx`（配置 dirty）用整图 JSON 序列化比较——大图上每次渲染 O(n) 序列化，且键序依赖运气。

### B7 · 测试分布不均

- 活跃组件 216 个 / 单测 87 个。新代（canvas chrome/run/AgentBar messages/Jobs）覆盖好；**空白区**：`Pipeline.ts`（引擎调度核心，只有 linear scenario）、`dataProvider.ts`（0 测试，80 个 case）、`OperationEditForm` 等旧代巨石。
- 正面对照：try-catch 纪律近乎完美（仅 `plugin/registry.ts`、`utils/filesystem.ts` 两处，均为 IO 边界，可白名单化）。

## 四、治理改动计划（G 系列）

> 纪律沿用施工手册：一任务一 commit（`<type>: <中文描述> (G1-01)`）、每任务 tsc 门禁、宿主机 `bun run quality` 期末集中验、**迁移类改动（纯搬运零行为变化）与行为改造绝不混 commit**。与 AgentBar 在改的 `pipelinesService/proposeActions` 相关项（G2-02）排在你那条线合并之后执行，避免冲突。

### G1 · 速赢期（每项 ≤0.5 天，可立即并行）

- **G1-01 共享格式化层**：新建 `apps/app/src/lib/format.ts`（`formatDuration/formatCost/formatTokens/timeAgo`，全部带单测）；替换 B3 列出的 6 处实现。验收：6 文件 0 本地 formatter，显示格式全站一致。
- **G1-02 `useJobControls` hook**：`apps/app/src/hooks/useJobControls.ts` 封装 pause/resume/cancel/rerun（含 ResultAsync、toast、onSettled refetch 回调）；JobsTable/JobDetailDrawer/TopPill/CheckpointDialog 四处改调。验收：`dataProvider.custom.*jobs/` 仅出现在 hook 与 dataProvider 本体。
- **G1-03 解除 canvas→AgentBar 反向依赖**：锚定计数改由 `workspaceStore` 承载（AgentBar 写入 `anchorCounts: Record<refId, number>`，GNodeShell 只读 workspaceStore）。验收：`grep -r "AgentBar" canvas/` 为空；现有徽标/线程测试不回归。
- **G1-04 `agentBarStore` Provider 化**：按 `createAgentBarStore(pipelineId)` + Context（照抄 workspaceStore 模式），消除跨 pipeline 消息闪现。验收：双 pipeline 切换单测（A 写消息→切 B→消息为空→切回 A→消息还在）。
- **G1-05 质量门补全**：宿主机执行 `bun run knip` 清零 + 写 `scripts/check-i18n-dead-keys.ts`（对比 locales 键与 `t("...")` 实际引用），两者挂入 `quality` 任务链；`vitest.config` exclude `src/archived/**`。验收：quality 含三道新闸且全绿。
- **G1-06 状态管理判据成文**：在 `CodeGuidelines.md` 增补一节：「跨页面真全局（toast/notification）→ 模块单例；随路由实体生命周期（pipeline/页面）→ Provider 工厂；二者不得混用」。验收：文档合入 + 现状标注例外清单。

### G2 · 结构期（每项 1–3 天，按序执行）

- **G2-01 dataProvider 注册表化**：`integrations/refine/resources/<resource>.ts` 一资源一文件，导出 `{ getList, getOne, create, update, deleteOne, custom }` 部分实现；`dataProvider.ts` 收缩为 `resourceHandlers` 查找 + 兜底报错（目标 ≤120 行）。custom url 改为常量枚举 `CustomEndpoint`。**纯迁移，零行为变化**，每 3–5 个资源一个 commit。验收：行为快照测试（每资源一条 happy path）+ 全站手测导航。
- **G2-02 pipelinesService 拆分**（等 AgentBar 线合并后）：`pipelinesService/` 下分 `crud.ts`、`proposeActions/`（已有目录，收编完整）、`analyzeIntent/`、`generateStructure/`、`optimize/`，`createPipelinesService.ts` 只做门面组装（≤100 行）。验收：现有服务单测全绿，无 import 路径外漏。
- **G2-03 行数红线整改批**（一文件一 commit）：
  1. `OperationEditForm` → 按表单分区拆 Section 组件 + `useOperationEditForm` hook；
  2. `SearchPipelineDialog` → `useGlobalSearch(query)` hook（七组 resolver 一组一文件）+ 纯渲染壳，顺带补 i18n（与 B2 合并处理）；
  3. `JobsCalendar` → 抽 `useWeekEvents(jobs, routines, weekStart)` 纯 hook（含单测），组件只渲染；
  4. `TopPill` → 抽 `usePipelinePersistence`（版本/dirty/save）+ `useRunControl`（接 G1-02）；
  5. `graphSlice` → compose/ungroup 几何计算下沉 `graphGeometry.ts` 纯函数（补针对性单测）；
  6. `SkillToOperationDialog` → 扫描/映射/提交三步拆分。
- **G2-04 archived 出 src**：`apps/app/src/archived` → 仓库根 `archive/app-legacy/`（不入任何 tsconfig/vitest/knip 范围）；`FolderBrowserDialog.stories` 的 storybookData 依赖内联化或删除该 story。验收：src 下无 archived；vitest 用例数下降但全绿。
- **G2-05 i18n 存量清欠**：B2 清单五个文件补 `t()`（en+zh），配合 G1-05 的死键检查形成闭环。

### G3 · 长期项（择机，需要单独立项）

- **G3-01 包图谱治理**：`plugin`+`plugins` 合并、`shared`+`utils` 合并（先 deprecation re-export 过渡一个版本）；`agent` vs `agent-engine` 职责写进各包 README 首段；`views` 标注 desktop 专用与退役计划。
- **G3-02 slice 类型工具**：封装 `createTypedSlice<TStore, TSlice>()` 帮助函数，消化 145 处 `as unknown as` —— 配合 zustand 官方 `StateCreator` 第四泛型的正确用法，目标降到 <10 处白名单。
- **G3-03 路由单轨化评估**：Hono REST 与 tRPC 双轨收敛为 tRPC 单轨 + 必要的 REST 适配薄层（外部集成保留）。先出 ADR（架构决策记录）再动手，因为牵涉 desktop/views 消费方。
- **G3-04 引擎与判定加固**：`Pipeline.ts` 补齐 fan-in/fan-out、checkpoint 恢复、cancel 中断三类 scenario 测试；TopPill/NodeConfig 的 JSON.stringify dirty 比较换成结构化版本号（graph 变更时 store 内递增 `graphRevision`，dirty = revision 对比，O(1)）。
