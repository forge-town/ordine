# ADR-001：包图谱与命名治理（agent/agent-engine、shared/utils、plugin/plugins）

> 状态：提议（H3-06 立项，等 H 系列合并后单独执行物理合并）
> 背景：治理审查 A2 指出 `packages/` 存在命名噪声——`agent` vs `agent-engine`、`plugin` vs `plugins`、`shared` vs `utils`，新人（含 coding agent）无法从名字推断职责归属。

## 决策

本 ADR 只确立**职责边界与合并取向**，不在 H 系列内执行物理合并（物理合并牵涉 desktop/views 消费方与大量 import 重写，单独立项）。

### 1. agent vs agent-engine —— 保留分立，已加 README 厘清（H1-05 完成）

- `@repo/agent` = runtime 适配层：每个 runtime 的 `run<Runtime>`、各自的 schema、runtime 无关的 `extractJsonFromText`。
- `@repo/agent-engine` = 调度 + 可观测性：`agentEngine.run` 选 driver、折算用量、记录 span。
- 结论：**不合并**。二者是清晰的"适配 vs 编排"两层，合并会把 5 个 runtime 子进程细节与调度/观测混在一起。README 已写明边界，命名噪声以文档消解即可。

### 2. shared vs utils —— 取向：合并为 `@repo/shared`，过渡期 re-export

- 现状：`shared` 多为领域错误类型/常量，`utils` 多为无依赖纯函数；两者边界模糊，新增工具常放错。
- 取向：以 `@repo/shared` 为单一通用层，`utils` 内容迁入并按子路径（`shared/fs`、`shared/text`）组织；旧 `@repo/utils` 保留一个版本周期的 deprecation re-export，再删除。
- 风险：消费面广，需一次性 import 重写 + knip 校验，单独立项。

### 3. plugin vs plugins —— 取向：保留分立但文档化

- `plugin` = 插件系统核心（registry/加载/类型），`plugins` = 内置插件实现。这是"框架 vs 实例"的合理分层，类似 `agent`/`agent-engine`。
- 结论：**不合并**；各自 README 首段写明"核心 vs 内置实现"，命名保留。

### 4. views —— 标注 desktop 专用与退役计划

- `views` 注释为 desktop 专用暂不动；本 ADR 记录其消费方仅 desktop-app，后续 desktop 形态确定后再决定并入 `ui` 或独立维护。

## 执行顺序（合并落地时）

1. 先补齐三对包的 README 职责段（agent/agent-engine 已于 H1-05 完成）。
2. shared+utils 合并：deprecation re-export → 消费方迁移 → knip 清零 → 删除旧包。
3. 每步独立 commit，`bun run check:boundaries` + knip 作为护栏。
